# QQ 绑定与站外通知：已知未处理项

本文件记录 PR #177 在 22 轮 codex review 中**明确识别、但决定不在本次改动里处理**的问题。
它们不影响功能可用，也不涉及数据安全，留作后续 backlog。

写下来的理由：这些不是"没发现"，是"发现了并决定先不动"。区别很重要 ——
下次有人碰到时不用重新推导一遍，也不会误以为是新问题。

## 前端并发（P2）

### 1. 未读计数跨口径的最后写入者竞争
`unreadCount` 由「含已读」与「仅未读」两种取数共写。已加 `countGeneration`
让最新一次写入胜出，但两次取数之间若发生新增/已读，较旧那次仍可能带来
短暂偏差，直到下一次刷新纠正。

**为什么先不动**：偏差窗口是一次请求往返，且下一次刷新即自愈；
彻底解决要把计数也按口径分存，会让三个 composable 的状态再翻一倍。

### 2. 变更作废在途 GET 时的 loading 闪烁
mutation 会 bump 世代号并替被作废的请求清 `loading`。若此刻另有更新的
GET 在跑，它的 loading 会被提前置 false，随后由它自己的 finally 再置一次。

**为什么先不动**：表现是转圈闪一下，自愈；精确处理需要按请求追踪在途计数。

## 投递器（P2/P3）

### 3. 目标快照复验的粒度
已加「快照超过 60 秒即强制重取并复验 bindingId」。但复验发生在**每个收件人
开始处理时**，若单个收件人的处理本身很慢（推送超时 5 秒 + 数据库往返），
理论上仍有秒级窗口。

**为什么先不动**：窗口从「整轮时长（可能数小时）」缩到「单次投递时长（秒级）」，
已经解决了问题的实质部分。

### 4. 统计口径与账本的完全对账
`summary` 的 sent/failed/suppressed 现已按实际参与投递的条数计，
但极端路径（部分抢占后整批退让、熔断中途 break）未逐一核对总和守恒。

**为什么先不动**：这些数字只用于运维日志，不驱动任何逻辑；
真实账目以 NotificationDelivery 表为准，`notify-inspect` 直接查表。

### 6. 重发循环内已读状态的二次时效性
重发前会批量查一次"哪些来源已被站内读掉"，但批次是串行处理的：
在这次批量查询之后、某个靠后批次真正发送之前被读掉的告警，仍会被推送。

**为什么先不动**：常规投递路径已在每批发送前单独复查（第 19 轮加的，
并用桩服务复现验证过）；重发路径的窗口是"一次批量查询到该批发送"之间，
且重发本身是异常路径（上一次投递失败才会有）。彻底解决需要把复查下沉到
每批发送前，与 revalidateTarget 一起做。

### 7. useAuth 多实例之间的取数竞争
`useAuth()` 的 in-flight 去重是每个实例各一份，通知设置面板与账号总览的
QQ 轮询各自持有一个实例。若前者捕获到 bound:false 的响应、却比后者
bound:true 的响应更晚返回，会覆盖共享的 auth-user 状态。

**为什么先不动**：需要把 in-flight 守卫提升为跨实例共享的 useState
（与三个 alerts composable 同款改造）。表现是渠道状态短暂过期，
下次刷新即纠正；而 useAuth 被全站使用，改动面远大于本 PR 范围。

## 基础设施（不属于本 PR）

### 5. user-backend 监听 `*:4455` 而非回环
服务暴露在所有网卡上。当前的 `trust proxy: 'loopback'` 策略对此是安全的
（外部直连时 socket 非回环，其 X-Forwarded-For 不被信任），
但服务本身可从外部访问仍是独立的收口问题。

**为什么先不动**：属于既有生产基础设施配置，改动监听地址需要单独确认，
不应混在功能 PR 里。

## 8. 长期关闭站内展示的类型仍会积累未读行

**现状**：站内开关切换时（两个方向）会把该类型此刻之前的未读一次性标为已读，
所以「重新开启后涌出一大堆积压」已经不会发生。但如果用户把某个类型**一直关着**
且不再改动设置，产出侧仍在为它写告警，这些行永远不会被读到，
而 `notify-retention` 只删已读的，于是它们会缓慢累积。

**为什么现在不做**：彻底解决要么让产出侧感知站内偏好（`PageMetricMonitorJob`
等三个来源都要改，且偏好属于展示层语义，下沉到产出侧会让两边耦合），
要么在保留策略里按「该用户关闭了这个类型」做清理（需要跨表关联偏好与三张
告警表，且要小心不误删 QQ 侧仍要用的行）。累积速度受限于用户自己的 watch 数量，
量级可控，不构成上线阻塞。

**如果要做**：倾向后者 —— 在 `notify-retention` 增加一个桶，
删除「类型已站内关闭 + 未读 + 早于 alertDays」的行，与既有桶同样默认 dry-run。
