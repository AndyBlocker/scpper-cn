# DEDUP：ListPages 跨批重复收敛与持久化跳过告警

## 1. 结论

L1 / Tier1 的 ListPages 多批结果现在先按 fullname 收敛：同一 fullname 保留按批号、
批内位置排序后的**最后一条完整观测**，再进入 diff、状态推进与快照。实现只在整行之间
选择，不会把两次响应的 rating、rating_votes、revisions 或 Tier1 元数据逐字段拼接；输出
的每一行都能逐字追溯到一次真实 AMC 响应。因此它不会制造远端从未同时存在过的状态。

这一语义处理的是活动集合 offset 分页的重复行本身。因页面新建/删除而恰好未被本轮
看到的另一页不会被误判为删除：L1 只推进本轮实际观察到的 fullname，不做缺席删除
推断；下一轮仍是完整重扫。每日 L1 枚举快照也只含唯一 fullname。

## 2. 异常放大阈值

阈值为：

```text
duplicate_fullname_rate = 重复行数 / 原始成功批行数
拒绝条件：duplicate_fullname_rate > 0.01%（0.0001）
```

选择依据不是直觉阈值，而是修复前活库的完整历史分布（2,609 轮 L1）：1 条重复 95 轮、
2 条 9 轮、3 条 1 轮，没有观察到 4 条。约 36,500 页时，3 条为 0.0082%，仍在阈值
内；4 条为 0.0110%，开始拒绝。当前问题中的 1--2 条约为 0.0027%--0.0055%，
有约 1.8 倍相对余量，但不允许成片重复无限放大。

越线时 `finalizeIncrementalListPagesRun()` 返回 `failed`；CLI 不持久化、不推进状态，
并由统一 run health 加入 `persistence_skipped` fatal reason，最终
`meta.ingest_run.status='failed'` 且进程 exit 1。异常轮既有结构化 `validation`、
`persistence.skipReason`、`persistenceSkipped=true`，也能被 systemd 单元失败直接告警，
不再是 exit 0 的静默 `partial`。L0/L1 在共享出口等待中命中时间预算的异常分支也改为
写同一事件并非零退出，避免另一条“无持久化但绿色”的旁路。

## 3. 修复前实测基线

查询库为 `scpper-v2`、端口 5434；修复起点为 2026-08-13 16:01 CST 左右。
滚动 24 小时 L1 为 280 轮，其中 18 轮跳过持久化（6.43%）：

| 原因 | 轮数 | 占全部 L1 |
| --- | ---: | ---: |
| 跨批重复 1 条 | 8 | 2.86% |
| 跨批重复 2 条 | 1 | 0.36% |
| 180 秒时间预算 | 6 | 2.14% |
| 首批无可信 pager / 首批失败 | 2 | 0.71% |
| 147 批中 1 批零星失败 | 1 | 0.36% |
| 合计 | 18 | 6.43% |

其中重复直接造成 9/280（3.21%）整轮丢弃。

## 4. 同类判据核查

`persistenceSkipped` / `partialEvidence` 的生产者只有 incremental-scan 的
`skippedPersistence()`。修复前 24 小时同一调用链的 L0 为 0/48，L1 为 18/280；
没有第二个隐藏的 marker 生产者。

共享的全字段 Tier1 路径没有这三个 marker，但同样以 `scan.status != ok` 阻止事实/SCD2
写入。它现在复用相同的末次观测收敛函数与 0.01% 阈值。活库可比 L3 样本 5 轮，
partial 0/5、跨批重复 0/5；样本小是因为 L3 正式频率为每周一次。

`parseHealthDecision.skipReason` 是 grep 命中的另一语义：它表示当前样本不足时不评价/
更新解析健康基线，不表示跳过采集持久化。修复前 24 小时它在 forum、page-identity、
tier2 分别触发 256/465、267/295、48/488；这些高比例值得单独做健康基线覆盖审计，
但没有“局部坏行否决整轮写入”的数据路径，不能与 `persistenceSkipped` 合并计数。

仍会拒绝 L1 整轮的其它条件及其实测触发率是：单批零星失败 1/280（0.36%，下轮完整
重扫收敛）、时间预算 6/280（2.14%，下轮重扫）、首批 pager/请求失败 2/280
（0.71%，已经是 failed/可告警）。其中单批失败仍是局部异常拒绝整体，但缺批无法知道
未观测 fullname 集合，不能安全推进全站投票基线；其明确收敛路径是五分钟后的完整重扫。

验收过程中还按实测触发而非 grep 外观修了三条收敛缺口：

- work-queue 在观察段 2/28 轮少领（1 轮是活库测试锁竞争，1 轮生产为 48/48）：原因是
  候选先裁成 limit 再 `SKIP LOCKED`。现保留一倍有序后备候选，最终仍只锁 limit；
  最终 L1 窗口 17/17 轮为 50/50。
- 300 秒 forum-consume 历史 154 轮中有 46 轮（29.87%）命中预算，仅 104 轮精确
  50/50/0。预算改为 360 秒：它等于 600 秒 systemd 硬超时的 60%，且相对旧参数成功
  轮 p95=270.0 秒留 90 秒余量；最终窗口 9/9，最终参数追加观察 2/2 均为 50/50/0。
- 两个持续 81 轮的 `votes_full` 漂移任务虽有入队路径，priority=72 却被同一 20--99
  老化带内的 22,961 条 catch-up 压住，实际 attempts=0。持久漂移现为 priority=200；
  两任务均在下一轮从 attempts 0→1 并成功 resolved。完整票扫描后还会在本地投影与保存
  的 L1 声明**精确相等**时立即 resolve；不等、缺字段或非整数仍留给下一轮 L1 复核。

## 5. 回归与静态检查

- 36,500 原始行中分别构造 1 条、2 条跨批重复：均 `status=ok`，重复页的 rating 等
  字段等于最后一次完整观测，持久化门不跳过。
- 36,500 原始行中 4 条重复：重复率超过 0.01%，`status=failed`。
- `persistenceSkipped=true`：run health 为 `failed`、reason 含
  `persistence_skipped`、exit code 为 1。
- 连续观察中另实际捕获 work-queue 48/48：认领 SQL 先把候选裁成 limit，再做
  `SKIP LOCKED`，两行短暂并发锁无法补位。现为锁定阶段保留最多一倍有序后备候选，
  最终仍按原 schedule 顺序只取 limit；构造前两行被另一事务锁定的回归可补足 4/4。
- `npx tsc --noEmit`：通过。
- `npm test`：最终完整重跑 553/553 通过。首次最终跑唯一失败是 420 秒 forum 预算违反
  既有“≤硬超时 60%”合同；修代码为 360 秒后重跑全绿，没有修改既有断言。
