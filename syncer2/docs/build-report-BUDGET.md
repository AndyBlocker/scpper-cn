# BUDGET：v2 出站限速分层与容量预算报告

## 技术结论

本次改造把“内部总量预算”和“站点拒绝压力”拆成两个独立控制器。预算控制器按越界比例限速，只负责把滚动速率压回预算；压力控制器继续使用既有 EGRESS/GATE 失败率判据和 0–3 档退避。最终请求间隔取两者要求的最大值，因此预算约束不会削弱站点保护，站点压力也不再被一次轻微预算越界伪造。

当前已启用链路的稳态容量估算为 **4,657 请求/小时**。加 15% 余量并向上取整到百位后，建议且已配置的预算为 **5,400 请求/小时**。`4,200` 比稳态需求少 457，无法容纳当前全部链路，不建议继续使用。

## 1. 比例预算响应

设滚动 60 分钟请求数为 `R`，预算为 `L`：

- `R <= L`：预算控制器关闭，不增加间隔；
- `R > L`：节流比例 `s = L / R`，所需降幅为 `1 - s`；
- 为避免当前滚动窗口已经超额时继续按过高瞬时速率发送，预算控制器将最小请求间隔设为 `ceil(3,600,000 / L)` 毫秒；
- 预算只有 `0/1` 两种状态，不复用压力控制器的 1–3 档，也没有固定冷却期；滚动量回到 `L` 以内立即退出。

在 `L = 5,400` 时，预算节流间隔为 667 ms：

| 场景 | 比例 `s` | 要求降幅 | 结果 |
|---|---:|---:|---|
| `R = 5,401` | 99.9815% | 0.0185% | 仅进入预算控制，不跳压力 level 3；目标速率不超过 5,400/h |
| `R = 10,800` | 50.0000% | 50.0000% | 仍将目标速率压回 5,400/h |

这使惩罚幅度与越界程度成比例，同时用预算速率对应的最小间隔形成硬上界。实现位于 `src/http/adaptiveEgress.ts` 的 `evaluateProportionalBudget`。

## 2. 两类原因的状态、冷却与恢复

| 控制器 | 触发条件 | 动作 | 冷却 | 恢复条件 |
|---|---|---|---|---|
| 预算 | 滚动 60 分钟 `R > L` | 独立 `budget_level = 1`，按 `L/R` 比例和预算间隔限速 | 无固定冷却 | `R <= L` 立即恢复 |
| 站点压力 | 连续两窗失败率 ≥5%，或单窗 ≥10% | 独立 `pressure_level` 逐级升档，沿用 333/667/2,000/8,000 ms 档位 | level 1/2/3 分别 30/45/60 分钟 | 冷却已过，且连续六个非空 5 分钟窗口失败率 ≤3%，每次降一级 |

连接、超时等传输层失败仍计入压力；HTTP 404 等确定性业务失败仍只进入分母、不进入压力失败数。原有单窗、双窗升档判据和六窗恢复判据均保留。最终限速间隔为：

```text
max(pressure_interval_ms, budget_min_interval_ms)
```

数据库用 `pressure_*`、`budget_*` 两组字段分别持久化原因、档位和时间；旧 `level/reason/recover_not_before` 只保留为有效状态的兼容镜像，不再作为控制器判定输入。

## 3. 低吞吐恢复不再自锁

升档仍以每 100 个请求的失败窗口判断，避免低样本误判站点压力；恢复证据改为固定 5 分钟时间窗：

- 只计算发生过请求的非空窗口，空窗不伪造健康证据；
- 连续六个非空窗口失败率均 ≤3% 才允许恢复；
- 恢复证据可在冷却期内积累，冷却结束后无需再等待 600 个请求；
- 任何超阈值恢复窗会清空连续健康计数。

因此在事故中的约 31 请求/小时下，每个 5 分钟窗平均仍约有 2.6 个请求，通常约 30–35 分钟即可形成六窗证据；level 3 的 60 分钟冷却成为主要恢复边界，而不是数小时才能凑满的 600 请求。回归用例只提供 7 个低频健康请求（每 5 分钟一个），验证在 60 分钟冷却后可从 level 3 恢复到 level 2。

## 4. 当前链路容量推导

容量定义集中在 `src/http/egressCapacity.ts`，每条链路均记录稳态请求量及推导依据：

| 链路 | 稳态请求/小时 | 依据 |
|---|---:|---|
| L1 | 1,740 | 每 5 分钟 145 请求，12 轮/小时 |
| work-queue | 1,300 | 活库小时峰值约 1,290，向上取整 |
| forum | 500 | 每分钟调度，链路 7.2 秒最小间隔形成上界 |
| image | 500 | 5 分钟调度，链路 7.2 秒最小间隔形成上界 |
| sitemap | 5 | 小时任务的当前请求量 |
| l0 | 2 | 每小时两轮 |
| resolve-pages | 10 | 当前低量链路峰值向上取整 |
| revision-source | 600 | 每轮 300 请求，每小时两轮 |
| **合计** | **4,657** | 各启用链路稳态之和 |
| **15% 余量** | **698.55** | 应对边界重叠、抖动和小幅增长 |
| **建议预算** | **5,400** | `ceil((4,657 × 1.15) / 100) × 100` |

活库近 7 天有效小时数据也支持主要分量：L1 平均约 1,694/h、峰值 1,802/h；work-queue 平均约 1,202/h、峰值 1,290/h。forum 与 image 使用链路节拍上界，避免仅按尚未充分爬升的历史样本低估。

`4,200 < 4,657`，即使不留余量也不足；相对建议值还差 1,200。`5,400` 能覆盖当前链路计划并保留 15% 余量，但它是内部容量预算，不是站点安全阈值；站点安全继续由独立压力控制器兜底。

## 5. 可检查性与迁移

迁移 `migrations/0058_egress_budget_pressure_split.sql` 已先于 TypeScript 代码生效，新增独立状态字段，将预算提升到 5,400，并写入容量计划版本和分项元数据。迁移可幂等重跑，不会在版本和预算均已正确时重置运行证据。

预算不足现在有三道检查：

1. `deriveEgressCapacityPlan` 从逐链路计划计算总量、余量和建议预算；
2. `npm run check:egress-capacity` 在构建或部署前失败退出；
3. `checks/0012_egress_capacity_budget.sql` 校验活库预算、策略版本、容量元数据和分离状态字段。

本次检查明确验证 `4,200` 会失败、`5,400` 会通过。以后新增链路或修改频率时必须同步更新容量计划；若未提高预算，检查会在运行前暴露缺口。

## 7. 运维边界与后续维护

- 链路节拍、批量大小、启用状态发生变化时，应先更新 `EGRESS_ROUTE_CAPACITY_PLAN`，再运行容量检查并迁移预算。
- 建议监控滚动量/预算比例；若稳态长期超过预算的 85%，应重新测算，而不是等待越界事件。
- 15% 是当前链路波动的工程余量；若 image/forum 实测稳定峰值显著高于 500/h，需按新节拍重新推导。
